# 优化协议（A 模式的执行细则）

## 一、判档

| 条件 | 档 | 动作 |
|---|---|---|
| 指令 ≥8 字，或含 ≥2 个信息点 | 完整优化 | 走全部七步 |
| 指令 <8 字且意图唯一（"翻译这个""改成正式点"） | 轻量优化 | 只补输出格式 + 1–2 条约束，不重排版 |
| 指令本身已是结构化 prompt | 只做减法 | 删冗余、补验收、调顺序，不动结构 |
| 用户要的是"回答"而不是"prompt" | 不优化 | 直接回答，末尾可附一句"想要 prompt 版就说" |

## 二、九维抽取表

| 维 | 从用户话里抓什么 | 用户没说时的默认值 |
|---|---|---|
| **任务** | 动词：分析/生成/改写/比较/实现/排查/抽取 | 取最保守的可验证动作（"列出""改写"） |
| **输入** | 材料是什么、在哪、多大、什么格式 | 写占位标签 <材料>，让用户粘贴 |
| **输出** | 形态（段落/列表/表格/JSON/代码/文件）、长度、语言 | Markdown + 结论先行 + 500 字内 + 中文 |
| **约束** | 必须做/不许做/边界条件 | 保留三条：不编造、不改原意、标不确定 |
| **上下文** | 谁用、什么场景、前因 | 一句话背景，写"背景：<一句话>"占位 |
| **受众** | 给谁看（领导/客户/新手/机器） | 懂行的同行，不解释基础概念 |
| **记忆** | 是否多轮、要不要沿用前文 | 单轮，不假设前文 |
| **成功标准** | 什么样算做完、怎么验 | 可核对：条数/字段/测试通过/字数 |
| **示例** | 有没有给正例反例 | 不给示例（DeepSeek 零样本更稳） |

九格里**至少填满 6 格**才算完整优化；少于 6 格回第 3 步补默认。

## 三、任务路由表

| 任务类型 | 骨架 | 必填块 | 高频坑 |
|---|---|---|---|
| 分析 / 决策 | 五块型 | 结论先行 + 依据条数 + 不确定标注 | 只写"分析一下"→ 输出全是综述 |
| 写作 / 材料 | 五块型 + 受众 | 文体、字数、口吻、结构（几段/几个小标题） | 没给文体 → 写成公众号腔 |
| 改写 / 润色 | 差分型 | 保留什么、改什么、改到什么程度 | 没写"保留"→ 事实被改掉 |
| 翻译 | 约束型 | 术语表、语体、是否本地化 | 没给术语 → 专有名词乱译 |
| 编程 / 修 bug | Agent 卡 | 目标、报错原文、相关文件、约束（只改必要文件）、验收（跑什么命令） | 没给报错 → 猜着改 |
| 代码审查 | 清单型 | 检查维度 + 严重度分级 + 输出表 | 没分级 → 全标"建议优化" |
| 数学 / 推理 | 推理型 | boxed 收答案 + 是否要过程 + max 档 | 又写"逐步思考"→ 重复引导 |
| 抽取 / 结构化 | Schema 型 | 字段名 + 类型 + 空值规则 + 输出 JSON | 只说"输出 JSON"→ 字段随机 |
| 分类 / 打标 | 批量型 | 标签集合封闭 + 边界规则 + 批量格式 | 标签开放 → 自造新类 |
| 检索 / 调研 | 检索型 | 子问题拆解 + 来源与日期 + 置信度 | 没要求来源 → 编引用 |
| Agent / 工具 | Agent 卡 | 可用工具、完成定义、失败处理、停止条件 | 没写停止条件 → 无限循环 |
| 角色扮演 / 创作 | 角色卡 | 人称、视角、篇幅、禁则、节奏 | 没写"不代替用户行动"→ 抢戏 |

## 四、压缩四刀

1. **删形容词**：高质量、专业、详细、深入、全面、尽可能 → 全删，改成数字或可判定条件。
2. **删礼貌与元话**：请、麻烦、帮我、我想让你、谢谢、如果可以的话 → 删。
3. **合同类**：三条讲格式的约束并成一条；重复的"不要编造"只留一次。
4. **一句一动作**：一句话塞两个动作就拆成编号。

判据：**删掉后输出质量不变 → 必须删**。经验值：一句话指令完整优化后通常 80–200 字，超 300 字就要怀疑注水。

## 五、模糊句 → 可执行句（六个句式）

| 原句 | 改法 | 结果 |
|---|---|---|
| 写得好一点 | 换成可验收 | "每条结论后给 1 条数据支撑，删掉所有形容词结论" |
| 详细说说 | 换成结构 | "分 3 部分，每部分 3 条，每条 1–2 句" |
| 专业一点 | 换成受众 | "写给有 3 年经验的工程师，术语直接用，不解释基础概念" |
| 别太长 | 换成字数 | "≤400 字，超出就删例子保结论" |
| 按我的风格 | 换成样本 | "参照下面这段的行文节奏与句长：<样例>" |
| 你懂的 | 换成显式条件 | "当 X 成立时做 A，否则做 B" |

## 六、两档范例

原句：`帮我看看这段代码有什么问题`

**轻量档（只要快速反馈）**

```
审查下面代码，输出表格：位置 | 问题 | 严重度（高/中/低）| 改法。只列真问题，不列风格偏好。

<代码>
（粘贴）
</代码>
```

**完整档（上线前检查）**

```
审查下面这段 Python 代码，目标是上线前排除会导致线上故障的问题。

<代码>
（粘贴）
</代码>

背景：FastAPI 服务，日均 20 万请求，前面有一层 nginx。

检查维度（按此顺序）：
1. 正确性：边界条件、空值、异常被吞
2. 并发：共享状态、竞态、连接池
3. 资源：未关闭的文件/连接、无界缓存
4. 安全：注入、越权、密钥硬编码

输出：Markdown 表格，列 = 行号 | 维度 | 问题 | 触发条件 | 严重度 | 最小改法。
规则：只报能导致故障的问题；风格类不进表；不确定标"待确认"；表后给 1 段"最该先修的一条"。

验收：表中每条都能对应到具体行号。
```

## 七、交付前自查（30 秒）

- 单独贴进新会话，模型在不知道任何背景时能否做对？不能 → 补上下文。
- 输出长什么样，我能不能一眼判断对错？不能 → 补验收标准。
- 有没有句子在"教模型怎么思考"？有 → 删。
- 有没有两个约束会打架？有 → 标优先级。
